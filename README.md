# Insurance Claims Intelligence — Microsoft Fabric demo

A self-contained walkthrough of **three Fabric surfaces over one set of data**, with a
data agent that routes between them by capability:

```
                        RF_Lakehouse  (8 Delta tables, synthetic claims data)
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   InsuranceSM      InsuranceOntology_      RF_Lakehouse
  (semantic model)      ManualGen            SQL endpoint
    metrics, DAX      graph traversal          full T-SQL
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
                        InsuranceAgent
                     (routes by capability)
```

The interesting part is the routing. Each surface can do something the others can't —
the semantic model aggregates, the ontology traverses relationships, and raw SQL
handles everything neither can express. The agent picks per question.

All data is **synthetic**, generated by notebook 01, spanning Jan–Mar 2026.

## Prerequisites

- A Microsoft Fabric workspace on an F SKU or trial capacity
- **Fabric IQ / Ontology** enabled in your tenant (preview) — required for notebook 02
- Permission to create lakehouses, notebooks, semantic models, and data agents

## Setup

Run in order. Each step depends on the one before it.

### 1. Lakehouse and data

Create a lakehouse named **`RF_Lakehouse`**, then run
[`notebooks/01_create_lakehouse_data.ipynb`](notebooks/01_create_lakehouse_data.ipynb)
with it attached as the default lakehouse.

Creates 8 Delta tables: `offices`, `policyholders`, `insured_assets`, `adjusters`,
`policies`, `claims`, `claim_events`, `asset_inspections`.

The generator deliberately plants the edge cases the demo questions depend on — NULL
payouts, claims above coverage, uninspected assets, over-capacity adjusters, incomplete
events. The final cell validates all of them are present.

### 2. Ontology

Run [`notebooks/02_create_ontology.ipynb`](notebooks/02_create_ontology.ipynb) in the
same workspace, same attached lakehouse.

Creates **`InsuranceOntology_ManualGen`** — 8 entity types, 10 relationship types, built
via the REST API with **data bindings included**.

> That's the point of the "ManualGen" name. The portal's click-to-generate button leaves
> data bindings *Unbound*, so no instances materialize and the graph is empty. Defining
> the bindings in code is what makes it queryable.

### 3. Semantic model

See [`semantic-model/README.md`](semantic-model/README.md).

Either import the supplied TMDL definition or build a Direct Lake model over the 8 tables.
Name it **`InsuranceSM`**.

### 4. Data agent

See [`data-agent/README.md`](data-agent/README.md).

Create **`InsuranceAgent`**, attach all three sources, and paste in the supplied
instructions, topics, and example queries. The 15 few-shot query pairs are the
highest-leverage part — they teach the agent the join paths and the traps.

## Data model

`claims` is the central fact table.

| Table | Grain | Notes |
|---|---|---|
| `claims` | one row per filed claim | `approved_amount` NULL until paid |
| `claim_events` | one row per action on a claim | `completed_at` NULL = incomplete; `cost_usd` is handling cost, **not** payout |
| `policies` | one row per policy | `coverage_amount` is the ceiling |
| `policyholders` | one row per person/org | |
| `insured_assets` | one row per asset | `last_inspection_date` NULL = never inspected |
| `adjusters` | claims staff | `max_active_claims` is a capacity ceiling, not a count |
| `offices` | branch offices | |
| `asset_inspections` | one row per inspection | |

Traps the configuration teaches the agent to avoid:

- **`approved_amount` is NULL, not 0.** `SUM` skips NULLs, so a raw payout total silently
  excludes unpaid claims.
- **There is no `closed` status.** Open = `NOT IN ('paid','denied')`.
- **Joining `claims` to `claim_events` fans out rows.** Aggregate events in a CTE first or
  counts and sums inflate.
- **Two adjuster paths.** `claims.adjuster_id` is assigned; `claim_events.adjuster_id`
  performed the work.
- **Three `status` columns** — on `claims`, `claim_events`, and `policies`.

## Notes

Synthetic data only; no real policyholders, claims, or personal information. Names,
addresses, and identifiers are generated from fixed seeds and any resemblance to real
entities is coincidental.

Ontology is a Fabric preview feature and its API surface may change.
